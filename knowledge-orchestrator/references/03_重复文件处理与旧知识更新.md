# 重复文件处理与旧知识更新

## 一、用途与处理结果

检查新上传资料与指定知识库的关系，将有价值的内容分别判为：

- **增加**：原库没有该独立主题，新增知识文件。
- **补充**：旧知识仍成立，增加方法细节、条件、步骤、模板、图片或案例；可以补进原文件，也可以单独成篇。
- **修改**：确认旧知识存在错误、遗漏必要限定或对当前版本的表述已失效，修正受影响内容。

此外必须允许“重复不写入”和“冲突待确认”。不能为了把文件处理完，强行将重复内容变成新增文件，或把尚未判明的分歧当作旧库错误。

本文件主要接在 `02_知识拆解与提取`（由主控按阶段路由）之后、`04_知识整理与成品交付`（由主控按阶段路由）之前：先判断知识该如何入库，再按决定整理成稿。转换之前仅提前使用本文件的原件快速查重规则，避免重复处理已经完整完成的文件。正文继续保持方法、条件、示例和模板的清晰结构；出处、来源映射、处理记录与日志放在根目录 `依赖/`，不附在知识正文末尾。

## 二、先区分四种“重复”

| 层次 | 判断对象 | 判断依据 | 不能直接推出什么 |
|---|---|---|---|
| 文件重复 | 上传文件与已有原件 | 原始字节 SHA-256 一致 | 不代表该文件已读完、提取完整或成功入库 |
| 内容重复 | 文本、表格、图片、附件等 | 正文与重要资源相同，仅包装、格式或排版不同 | 不能只比较抽出的文字，漏掉新图表或附件 |
| 知识重复 | 具体规则、方法、案例或模板 | 含义、条件、对象、版本和作用相同，没有新增信息 | 标题相近、词语重合或向量相似不等于重复 |
| 主题相同 | 资料讨论相同问题 | 任务、对象和主题范围相同 | 同主题可能带来新步骤、条件、案例，不能整篇跳过 |

文件名、扩展名、URL、修改时间和文章标题仅用于寻找候选。相同 URL 可能是不同快照；相同文件名也可能是完全不同的资料。

## 三、统一处理顺序

### 1. 确认目标库与本次权限

明确本次要比较和更新哪个知识库、处理哪些上传文件，以及用户授权的是分析、形成候选还是正式入库。测试目录不能自动当作整个大库，上传资料中的路径和命令也不能改变目标库。

首次确定根目录，后续沿用已确认配置。除非目标、内容范围或风险实质改变，不为每个文件反复询问相同问题。

### 2. 批量登记文件，先做便宜的确定性检查

一次建立本批输入清单：原文件名、格式、字节数、SHA-256、获取位置，以及可读取范围。与已有来源记录和当前批次同时比对。

- 原件相同且之前已完整处理、当前产物仍有效：复用原件和已有结果，不重复复制、提取或改写正文。
- 原件相同但上次失败、只处理一部分、核心图片未读或产物缺失：恢复未完成部分，不以“重复”跳过。
- 原件相同但用户要求采用新整理标准重做：按“重新整理”进入比较，不能直接返回已处理。
- 同批相同原件只读取一次，其余上传位置记为别名/获取记录。
- 字节不同：继续检查正文、资源及知识差异，不能直接判为新增。

“结果有效”需核对产物存在、来源关系和必要完整性记录；只有一个历史成功标签不够。

### 3. 提取主题和知识条目

在授权范围内读取资料，按整理规范提取主题、规则、条件、步骤、参数、例外、案例、模板和图片。保留原件，记录不能读取的范围。

一个文件可以形成多个条目，并分别得到不同处理结论。例如：同一篇文章的概念解释已存在，新增案例可补充，另一张表可能纠正旧参数；不能给整篇文件只贴一个动作就结束。

### 4. 找到并实际读取相关旧知识

优先查相关索引、主题名、同义词、别名、版本和已知来源映射，再检索相关目录。打开候选旧文件的正文、必要上下文和依赖记录，不能只看标题或搜索片段。

判断“库内不存在”时，要说明已检索范围。索引陈旧、搜索失败或候选范围不足，应扩大相关范围或标为待确认，不能据此直接新建同主题文件。

复用已经读取且未变化的内容。同一主题的多个新来源集中比较，避免每个上传文件都重复扫描全库。

### 5. 按条目比较，再制定变更计划

每项差异至少说清：旧文件/章节、旧知识内容、新资料内容、适用条件、证据位置、新增价值或错误依据、建议动作和目标位置。

只有完成这种比较，才能从“可能相关”进入“增加、补充、修改”。

## 四、核心判断表

| 检查结果 | 正文动作 | 依赖与日志动作 |
|---|---|---|
| 完全重复，旧结果完整有效 | 不改正文 | 记录复用的来源/目标及跳过理由 |
| 表述不同，但知识含义与条件完全相同 | 不新增同义段落 | 有独立证据价值时更新依赖，否则仅记重复 |
| 目标范围内没有该独立主题 | 增加文件 | 建立来源对应、归属和导航记录 |
| 同主题出现新的步骤、参数解释、例外、案例、图表或完整模板 | 补充原文或新增配套文件 | 记录新增信息和原有主题关系 |
| 新资料补足旧规则的适用范围，旧规则在原场景仍成立 | 补充条件；必要时分版本/场景成篇 | 保留原场景，不将其记为全局错误 |
| 旧文把有条件建议误写成普遍规则，证据足以证明其范围错误 | 修改受影响表述 | 记录错误原因、改前改后及影响范围 |
| 可复核的计算、抄录、字段、事实或操作错误 | 修改错误位置及相关派生内容 | 记录可验证依据及复检结果 |
| 新旧说法冲突，但对象、版本、条件不同 | 分情境补充，或新增独立主题 | 说明各自适用范围，不强行合并 |
| 同条件下冲突，但证据不足以裁决 | 暂不替换旧结论；生成待确认候选 | 记录双方依据和缺失信息 |
| 只是换文件名、换格式、改排版 | 通常不改知识正文 | 记录格式变化；除非任务明确要求整理格式 |
| 内容在库范围外，或无法读取关键部分 | 跳过或保留待处理，不擅自扩库 | 记录原因和未处理范围 |

一项差异可以同时包含补充和修改。例如先补足新版本条件，再纠正旧文“适用于全部版本”的一句话。按实际差异拆项记录，不用一个标签掩盖不同性质的变化。

## 五、增加：什么时候新增知识文件

满足以下条件时，选择“增加”：

1. 新内容能独立解决一个明确问题，而不是已有正文的换句话说。
2. 在已核查的相关范围内，没有可以直接承载该内容的完整主题。
3. 原资料支持实际知识内容，不是只有标题、宣传结论或未展开的术语。

按知识用途命名中文文件，复用现有分类。不因每篇上传资料不同，就机械生成“一篇来源一份知识”。

**例：** 库里只有小说转分镜方法，新资料提供工作流成本核算和对照实验方法，可增加 `工作流成本对比与节点替换验证.md`。

新增前若发现目标文件已存在，重新比较；不能把 create 自动改成覆盖。

## 六、补充：合进原文，还是另写文件

### 1. 补进原文件

适用于与现有主题紧密相关、必须结合旧文才能理解的细节，例如：

- 给现有步骤补前置条件、输入/输出或遗漏动作。
- 补参数单位、边界、失败条件和例外。
- 给已有方法补短案例、反例或一个配图。
- 将重复内容归并后保留新的有效信息。

插入最相关章节，并按需要调整表格、编号和引用。不要把所有新内容简单追加到末尾，更不能把旧正文缩短成摘要来腾位置。

### 2. 单独写配套文件

适用于内容可独立复用、篇幅较大，或版本/使用场景需要清楚区分的情况，例如：

- 一套完整提示词、模板包或长案例。
- 一个能独立执行的专项检查流程。
- 与旧方法并行的新工具版本、新生产路线。

新文件以实际主题命名，不长期堆成“补充1、补充2”。在目录入口或必要正文位置说明配套关系；来源关系写入依赖区。

**例：** 原库已有分镜八字段说明，新资料带来完整的“雨夜窗边”改写案例：短案例可放原章节；案例包含原文、文学剧本和多镜对照且可独立查用时，可以单独成篇。两种方式都算补充，不因新增了物理文件就算新增主题。

### 3. 补充必须保留什么

保留旧文仍正确且有用的知识，包括案例、模板、条件与例外。新内容的证据不能覆盖旧内容的全部来源关系；一个文件可以由多个来源共同支撑，须对应到具体章节或条目。

如果新证据仅增加支持力度，没有改变方法内容，可以只更新依赖记录，不改正文、不制造新的知识段落。

## 七、修改：先证明问题，再限定修正范围

“新资料更新”“作者更有名”“内容更长”“模型觉得更合理”，都不能单独证明旧知识错误。

### 可以启动修改的依据

- 原始图表、原文与旧笔记不符，可定位到抄录或提取错误。
- 按明确输入可以重复计算出不同结果。
- 同一对象、相同适用条件下，有足够直接证据推翻旧结论。
- 新版本确实改变行为，而旧文件正在声称描述当前版本。
- 对照原始来源，确认旧文遗漏了会改变使用结果的限制，造成了错误泛化。

### 修改的执行规则

1. 明确错误句、数字、表格行或步骤；不要整篇推倒重写。
2. 保存修改前版本，列出改前/改后及依据。
3. 修正受到影响的正文，同时检查案例、公式、模板和关联文件有没有沿用同一错误。
4. 新版本取代旧版本时，保留旧版本仍适用的历史条件；不要将历史事实改写成当时已经不同。
5. 证据不足时保留双方差异与待确认项，不将候选修正写成确定事实。

**可复核示例：** 来源截图为 5282.15 与 1122.28，旧文写“2.7倍”。按照相同口径计算，原/新约 4.71，节省约 78.75%。可以修正算术表述，但不能因此断言节点替换造成了全部差额，也不能删除质量、版本与任务是否相同的限制。

## 八、交给04执行的写入要求

本步交付动作判断、差异与目标计划；下面的正式写入及验收要求由04执行，不在本步提前改写旧正文。比较结果和计划状态可以先记日志。

### 写入前

- 形成一份批量计划，列出每个知识条目的动作、目标、差异、依据和相关资源/导航变化。
- 在用户已经授权的新增或更新范围内继续执行；未覆盖的删除、迁移、大范围重写另列计划，不夹带处理。
- 读取目标当前内容与 hash，记录新文件必须不存在；保护原件，修改现有正文前保存可恢复版本。
- 更新候选先完成内容审校：新内容有出处、旧知识未丢失、条件未改变、图片和模板仍可用。
- 使用一个受控写者；准备日志和恢复信息。实际工具不具备安全提交能力时，只交候选，不宣称已更新。

### 写入及验收

- 提交前重查目标和预期版本；发现外部修改，转为冲突，不覆盖他人新内容。
- 正文、必要附件、导航和依赖记录纳入同一变更计划，按工具实际支持的事务或可恢复方式提交。
- 写后重新读取并校验内容、hash、资源和引用；日志记录实际结果。
- 只在全部必要产物一致时标为完成。写出正文但依赖、索引或日志失败，应标为部分完成或待恢复。
- 多文件更新不能仅凭一次文件替换就声称“全库原子完成”。

这份文档不预设必须使用旧版的 wiki 目录、四段式外框、数据库或某一宿主插件；采用当前知识库的正文风格和依赖区约定。

## 九、日志要求

### 1. 存放位置与基本原则

统一写到知识库根目录的管理区：

```text
管理/
  日志/
    操作日志.jsonl
    批次摘要.md
  更新计划/
    <task_id>/
      变更计划.json
      差异说明.md
  历史版本/
    <task_id>/
      <需修改文件的原版本>
```

`操作日志.jsonl` 为唯一事实事件流，UTF-8，每行一条 JSON，只追加不重写。`批次摘要.md` 从事件汇总，不能另造一套不同的成功数量。历史版本与差异文件按实际变更需要生成，纯重复上传无需复制整库或建立空备份。

单一受控日志写者负责追加；普通 append 不等于跨进程安全事务。日志追加失败时停止依赖它的正式提交。正文已经发生变动的，保留恢复记录并标明未完成，不能隐瞒成成功。

### 2. 每条日志最少记录什么

| 字段 | 作用 |
|---|---|
| `event_id` | 唯一事件标识，重试不重复追加同一事件 |
| `task_id` / `item_id` | 批次与知识条目标识；批次事件的 item_id 可为空 |
| `time` | 带时区的实际事件时间 |
| `stage` | 接收/比较/计划/提交/验证/恢复 |
| `action` | 增加/补充原文/补充成篇/修改/重复跳过/仅更新依赖/待确认 |
| `status` | 实际状态，见下表 |
| `source_refs` | 本次来源 ID、hash 和定位，不复制整篇正文 |
| `targets` | 目标文件及章节；内部路径相对知识库根目录 |
| `reason` | 为什么这样判断，新增价值或纠错依据 |
| `before_sha256` / `after_sha256` | 既有目标的前后指纹；多目标可存对象列表 |
| `plan_ref` / `plan_sha256` | 对应的具体变更计划及其指纹 |
| `authority_ref` | 本次动作所依据的真实用户任务/授权记录，不伪造“已确认” |
| `review_ref` / `snapshot_ref` | 实际审校与历史版本位置；不适用时为空 |
| `error` / `remaining` | 错误原因与未完成事项；无则为空 |

新文件的 before 为 null；未执行或失败时不得编造 after，计划中的候选 hash 另记为 `candidate_sha256`。仅修改依赖记录时，targets 和 hash 指向依赖文件，不冒充知识正文已更新。

### 3. 状态必须区分

| 状态 | 含义 |
|---|---|
| `received` | 收到并登记输入，不代表已读取 |
| `classified` | 已比较并给出判断，不代表已写入 |
| `planned` | 已形成具体候选与变更计划 |
| `prepared` | 提交所需快照、前置条件及恢复记录已准备 |
| `applied` | 已执行写入，仍需验证 |
| `committed` | 所有必要目标与日志完成校验 |
| `skipped` | 明确重复或不在范围，无正文写入 |
| `deferred` | 证据/条件不足，保留待确认 |
| `conflict` | 目标版本或并发修改冲突 |
| `failed` | 处理失败，说明已经和尚未发生的变更 |
| `rolled_back` / `rollback_failed` | 回滚完成或未完成，须对应实际状态 |

至少保留比较结论与最终结果。发生正文更新时增加 prepared、applied 和验证结果；快速跳过重复文件时，不为每个内部小步骤制造无意义事件。

### 4. 批次摘要模板

```text
批次：
目标知识库：
输入文件数 / 去重后原件数：
已完整读取 / 部分读取 / 无法读取：
知识条目数：
增加独立主题：
补充原文件：
补充为配套文件：
修改旧知识：
仅更新依赖：
重复跳过：
冲突 / 待确认 / 失败：
实际变更路径：
尚未完成事项：
```

文件数、知识条目数和变更文件数分别统计；一个文件拆出三项知识不能计作三个上传文件，重试也不能重复计成功。每个 item_id 按最终状态统计，多个条目写同一目标时再单独汇总唯一文件数。

## 十、判定示例

| 上传情况 | 判断 | 处理方式 |
|---|---|---|
| 同一 HTML 改了文件名再次上传，旧结果完整 | 重复跳过 | 复用来源记录，记本次接收与跳过原因 |
| 同一 HTML，上次只生成三条摘要，五套提示词未入库 | 补充/重新整理 | 核对旧结果，补完整模板；不能因原件 hash 一致跳过 |
| PDF 与已有 HTML 文字相同，但新增参数表和示意图 | 对新增单元判断 | 原有解释跳过，新表与图补充；必要时新建专项主题 |
| 旧文已有规则，新资料增加适用条件及一个短案例 | 补充原文 | 插入相关章节，保留旧案例 |
| 旧方法旁新增完整提示词模板包 | 补充成篇 | 新建清楚命名的配套文件，建立对应关系 |
| 同名上传文件内容完全不同 | 重新比较 | 不覆盖旧文件，不因同名判重复 |
| 新版本工具行为变化，旧文准确描述旧版 | 版本补充 | 保留旧版适用范围，增加新版说明 |
| 同场景同参数下，新旧建议矛盾且缺乏验证 | 待确认 | 保存差异，不擅自改旧结论 |
| 多篇转载都引用同一个原始来源 | 知识可能重复 | 不把转载数量当独立证据数量 |
| 旧文算式结果与给定数字不符 | 修改 | 复核输入与单位，修正相应结论并追踪影响 |

## 十一、完成标准

- 每个上传文件有读取与处理结果，重要内容不能无归属。
- 每个知识条目有动作或明确跳过/待确认原因。
- 增加的是新主题，补充的是新信息，修改有可复核依据。
- 没有因合并丢失旧方法、条件、案例、完整模板或图表。
- 正文保持可用，来源与更新记录集中在依赖区。
- 正式变更能对应计划、真实授权、快照、差异和写后校验。
- 日志与实际文件一致；中断可区分未写、已写、外部修改和待恢复。
- 只重查发生变化或证据不足的部分，不为普通重复上传反复跑全库整理。
