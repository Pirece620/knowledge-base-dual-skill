# 统一日志与交付

## 一、路径与职责

正式写入前读取[目录结构与自动归档](目录结构与自动归档.md)。正式目标库明确且允许任务记录时，唯一事实事件流为`管理/日志/操作日志.jsonl`。纯只读咨询不强制改库；仅转换/试稿或目标尚未明确时，在已授权工作区相同相对路径记录，不偷偷往正式库落日志。

主控负责最终汇总。工人有同一task_id时只提交本阶段事实，不能另记全任务完成。独立处理器记录自己的实际阶段，不虚构主控调用。

真实事件保留event_id、task_id、time、stage、action、status、targets、reason；有依据时加入source_refs、plan_ref/plan_sha256、before/after_sha256、review_ref、snapshot_ref、error与remaining。

状态区分received/classified/planned/prepared/applied/committed/skipped/deferred/conflict/failed/rolled_back/rollback_failed。未执行不得写after hash或committed；候选hash叫candidate_sha256。统计按唯一输入、条目和最终目标分别计算，不按事件行数或重试次数计成功。

## 二、日志帮助脚本

`python scripts/knowledge_io.py --help`查看接口；从实际Skill目录解析脚本绝对路径，不写死安装位置，使用可用的Python 3.11+。

- `layout --root ROOT [--topic 主题]`：缺少目录和0号入口就创建；已有目录和入口复用，不覆盖。主题由Agent依据知识内容确定。
- `hash PATH...`：只读计算原文件指纹。
- `verify --root ROOT --manifest FILE`：验证`knowledge-artifacts.v1`中的artifacts，每项含根相对path和sha256；不存在、改变、越界或联接均失败。
- `record --root ROOT --event FILE`：将实际事件追加到固定日志路径，使用系统文件锁，按event_id幂等去重；同ID不同内容拒绝。它不推断成功，也不替Agent生成授权。

必须先写好真实事件JSON再调用record，不能把这里的说明当作已执行。所有字段需要Agent依据实际操作填写。程序校验不代表语义审校、权限审查或跨文件事务保证。

## 三、正式发布

在既有授权内执行，不重复询问低风险新建。修改现有知识先形成具体差异；需要的新授权应绑定可审阅计划，不能凭“上传文件”推断允许任意覆盖、删除或迁移。

计划包含正文、资源、相关0号/导航与依赖记录，以及目标当前hash、候选hash和操作。原件不变，修改前保留可恢复版本；一个受控发布者执行。

最终写入必须用宿主真实可用的独占/条件写入或可恢复事务能力。只检查hash后再普通覆盖并不消除竞争；不能保证时保留候选，不强写。已有授权持续有效，不能以阶段交接为由重复索取。

日志先记录准备，写后重读所有必要产物，再记真实结果。日志失败、外部编辑、资源或索引不一致时，不能报全任务完成。已发生修改要说明实际范围并保留恢复依据，不伪装成“什么都没做”。

## 四、结果呈现

给用户看实际增加、补充、修改、跳过与待确认，以及入口文件和必要限制。具体出处、hash、验证记录、版本说明保留在根目录依赖区，不加到知识正文末尾。

不自动创建Git检查点、全库备份或全库重排。不因原文说“经过测试”就声称本次做过实测。阶段状态和产物hash核对通过，也不等于所有模型、格式和宿主都经过测试。

每个实际处理批次另在`依赖/`形成一份可读Markdown说明，链接本批输入、知识文件、附件分组与管理记录。日志与批次依赖说明各有用途，不互相替代。
